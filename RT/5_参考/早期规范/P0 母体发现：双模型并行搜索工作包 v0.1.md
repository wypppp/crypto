# P0 母体发现：双模型并行搜索工作包 v0.1

## 0. 总任务

目标不是证明任何交易策略有效，而是对第一批 10 个 P0 母体进行高效率桌面调查，回答：

> 哪些母体值得进入下一轮 Mother-set Census / W00，哪些应当 WATCH、合并、拆分或淘汰？

第一轮禁止：

- 开始实现 indexer；
- 开始写 W01 pipeline；
- 因看到某个历史赢家而深挖钱包；
- 把历史最高价格直接称作 executable `M*`；
- 给出三年赚钱概率；
- 因某工具容易使用而改变母体定义。

第一轮允许：

- 不完整但有来源的规模估计；
- `PRICE_TAIL_LEAD` / `MCAP_TAIL_LEAD`；
- 对未知明确标 UNKNOWN；
- 对极新的母体给 `CAPTURE_NOW`；
- 发现母体定义错误后合并或拆分。

# 2. 模型 A 工作包：DISCOVERY / SCALE

## 角色

```text
MODEL_A_ROLE = HIGH_RECALL_DISCOVERY
```

模型 A 优先优化：

> Recall > Precision

宁可把一个可疑母体留给 B 反证，也不要因为首轮资料不完整而误杀。

A 不负责证明 executable return，不负责审计 SDK 的每个实现细节。

---

## A1. 每个母体必须回答的 6 个问题

### A-01 母体是什么

给出暂定定义：

```text
chain
platform / protocol
launch mechanism
asset stage
candidate unit
time/version boundary
```

明确：

> “一个候选到底是什么？”

例如：

- 一次 token creation？
- 一个 bonding-curve pool？
- 一个 creator coin？
- 一个 agent launch？

---

### A-02 当前是否还活跃

至少找一种最近活动证据：

- 近 7 天；
- 近 30 天；
- 若没有则近 90 天。

优先估计：

```text
launches
graduates / migrations
active pools
volume
fees
```

不要求每项都有。

记录：

```text
scale_estimate
scale_period
scale_definition
scale_source
```

---

### A-03 有没有巨大右尾迹象

寻找历史或近期：

```text
>=10x
>=50x
>=100x
```

但第一轮只标：

```text
PRICE_TAIL_LEAD
MCAP_TAIL_LEAD
PLATFORM_REPORTED_TAIL
UNKNOWN
```

严禁写：

```text
EXECUTABLE_100X
```

除非已有研究真的按固定规模和执行成本证明过。

至少保存：

```text
asset
approx_multiple
start_reference
end_reference
source
known_bias
```

---

### A-04 普通用户是否原则上能在右尾形成前进入

只做粗筛：

```text
PUBLIC_BEFORE_TAIL
PUBLIC_BUT_LATE
PRIVATE / WHITELISTED
UNCLEAR
```

查：

- launch 是否 permissionless；
- 是否公开 bonding curve；
- 是否 TGE 后才有公众交易；
- 是否只有私募价才能形成所谓 100×；
- 是否明显属于无法参与的 allocation。

---

### A-05 有没有办法形成分母

寻找最直接的 enumeration lead：

```text
factory/program event
official API
platform API
Dune table/query
indexer
contract logs
launch feed
historical dataset
```

只回答：

> “看起来有没有可行入口？”

不要部署。

---

### A-06 已有研究做到哪里

查：

```text
arXiv / papers
GitHub analyses
Dune dashboards
public notebooks
protocol analytics
serious research threads
```

特别记录已经测过：

- launch frequency；
- graduation；
- holder profitability；
- manipulation；
- predictors；
- returns；
- execution。

避免后续重复研究。

# 4. 模型 A 的停止规则

单个母体满足以下条件即可停止，不继续“搜全互联网”：

### `A_COMPLETE`

已经得到：

```text
mother-set tentative definition
+
current activity estimate
+
至少一个 tail lead 或明确没有发现
+
public-access rough judgment
+
至少一个 enumeration lead
+
主要 prior work
```

### `A_EARLY_DROP_LEAD`

可以提前停止搜细节，如果出现明显：

```text
平台基本死亡
AND
历史也缺巨大右尾线索
```

但只建议 `DROP_CANDIDATE`，最终 DROP 由合并裁决决定。

### `A_CAPTURE_NOW`

新母体历史太短但：

```text
launch rate 高
+
数据易失
+
公开可进入
```

则停止历史深挖，标记建议立即前向保存。

# 6. 模型 B 每个母体必须做的 7 类检查

## B-01 这真的是独立母体吗

检查：

- 是否只是同一个 factory 的不同 frontend？
- 是否共享同一个 program / Platform PDA / config？
- 是否品牌不同但经济机制相同？
- 是否一个品牌内部其实存在多个完全不同机制？

输出：

```text
KEEP_INDEPENDENT
MERGE_WITH:<id>
SPLIT_REQUIRED
UNRESOLVED
```

并说明“按什么经济单位区分”。

---

## B-02 生命周期是否被 A 简化错了

主动找：

```text
migration
graduation
AMM transition
v1/v2/v3/v4
deprecated
breaking change
token migration
fee change
vesting
locking
partial fill
router change
```

尤其检查：

> entry venue 和 exit venue 是否可能不同？

输出简版：

```text
STATE_0
→ transition
→ STATE_1
→ transition
→ STATE_2
```

只列会改变交易/测量的边界。

---

## B-03 Tail evidence 是不是假的

逐个攻击 A 的右尾 leads：

常见错误：

```text
market cap 100x ≠ 可兑现 100x
private-sale price → public peak
survivorship bias
极薄池最后成交价
错误 decimals
token redenomination
migration 前后价格单位变化
rebase
honeypot / cannot sell
只有极小 Q 可实现
```

为每条 A tail lead 给：

```text
PLAUSIBLE
WEAK
INVALID
UNRESOLVED
```

第一轮不要求重算完整 `M*`。

---

## B-04 分母路径能不能真的成立

检查 A 提出的：

- official API；
- Dune；
- factory；
- Carbon；
- third-party indexer；
- leaderboard。

重点问：

```text
能不能看到失败发行？
能不能看到已消失对象？
能不能重建过去窗口？
有时间边界吗？
有 version 边界吗？
是否只返回 survivors？
分页会不会漏？
当前榜单是不是被当历史全集？
```

输出：

```text
ENUMERATION:
  likely_complete
  partial_but_repairable
  platform_visible_only
  current_survivors_only
  unsuitable
  unknown
```

---

## B-05 来源是不是假独立

记录重要来源的上游谱系。

例如：

```text
Dashboard A → Helius
Dashboard B → Helius
Article C → Dashboard A
```

不能把三个页面算三个独立数据源。

只针对承重 claim 检查，不做全网 provenance graph。

---

# 11. A/B 合并后的裁决规则

不是多数投票。

按以下逻辑：

### A=ADVANCE，B=ADVANCE

```text
→ ADVANCE
```

进入第二轮 Mother-set Census。

---

### A=ADVANCE，B=WATCH/UNRESOLVED

```text
→ TARGETED_CHECK
```

只解决 B 指出的 1–3 个承重问题。

不要重做整个搜索。

---

### A=ADVANCE，B=DROP

必须列明：

```text
B 的决定性反证是什么？
```

如果是：

- 数据明显错；
- 不可参与；
- 母体不存在；
- 右尾基准错误；

则优先接受 B。

如果只是：

> 数据还不充分，

则应为：

```text
UNRESOLVED
```

而不是 DROP。

---

### A 找到新母体，B 证明与现有母体重复

```text
→ MERGE
```

保留 A 的信息，但不增加一个新分母。

---

### B 发现一个品牌实际包含两种经济机制

```text
→ SPLIT
```

例如：

```text
Virtuals Standard
≠
Virtuals Genesis
```

以后分别研究。
