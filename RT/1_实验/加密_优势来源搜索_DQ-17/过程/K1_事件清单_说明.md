# K1 事件清单说明

产出文件：`../raw/K1_events.csv`（232 行，upbit 127 行 / bithumb 105 行）。本文件只做事件清单收集，不算任何收益、涨幅或价格路径。

## 1. 数据来源和接口

### 1.1 Upbit（公告 + 现价市场列表）

- 公告列表：`GET https://api-manager.upbit.com/api/v1/announcements?os=web&page={n}&per_page=30&category=trade`（官方接口，无需鉴权；`per_page` 超过 30~49 之间某个值会 400，实测 30 稳定可用）。抓取 `category=trade`（"거래"分类）下的全部公告，倒序分页直到最早一条早于 2025-09-20（留出缓冲），共翻 7 页，拿到 210 条（覆盖到 2025-08-22）。
- 公告详情（含正文 body、原始发布时间 `first_listed_at`、最新展示时间 `listed_at`）：`GET https://api-manager.upbit.com/api/v1/announcements/{id}?os=web`。对列表中标题命中筛选条件（含"신규 거래지원 안내"或"마켓 디지털 자산 추가"）且落在 2025-09-23~2026-09-22（UTC）窗口内的 106 条公告逐条取详情。
- 当前市场列表（用于"此前是否已上线"兜底判断）：`GET https://api.upbit.com/v1/market/all?isDetails=false`，取 2026-09-23 时点的 KRW 市场列表（289 个）。
- 以上三个接口均可直接访问，无 Cloudflare 或地域限制。

### 1.2 Bithumb（公告）

- 官方 Public API `GET https://api.bithumb.com/v1/notices` 实测**只支持 `count`（1~20，默认 5）参数，不支持翻页（page/offset）和分类过滤**（apidocs.bithumb.com 页面已核实：只有 `count` 一个参数），因此无法用它回溯一年前的公告，只用于确认接口存在。
- 网页版公告列表 `https://feed.bithumb.com/notice*` 有 Cloudflare"Attention Required"人机验证拦截，直接 `curl` 返回 403。改用免费公开的只读代理 `https://r.jina.ai/<目标URL>` 抓取（该代理会把目标页渲染后的 HTML/Markdown 返回，未见收费墙，不需要注册账号）。代理请求同样会被 Cloudflare 间歇性拦截，需要退避重试（观察到约每 12~25 秒 1 次请求比较稳定，过快会连续 403/"Attention Required"）。
- 通过代理拿到页面里 Next.js 的 `__NEXT_DATA__` JSON（`pageProps.noticeList`），确认"마켓 추가"（市场新增）分类 `category id=9`，用 `https://feed.bithumb.com/notice?category=9&page={n}` 翻页，共翻 4 页拿到 120 条（覆盖到 2025-06-27），过滤出窗口内（2025-09-23~2026-09-22 UTC）94 条公告。
- 各条公告详情正文：用同一代理抓 `https://feed.bithumb.com/notice/{id}`，解析正文里的"거래 개시 시점 : ..."（交易开始时点）逐资产小节，用于补全标题里没写开盘时间的公告。
- 当前市场列表：`GET https://api.bithumb.com/v1/market/all?isDetails=false`，2026-09-23 时点 KRW 市场 480 个，另有 13 个遗留 BTC 计价市场（均为老牌资产，与本次新增无关，已核实"마켓 추가"分类下 94 条全部是"원화 마켓 추가"即 KRW 市场新增，没有 BTC/USDT 市场新增混在这个分类里）。

### 1.3 币安 / Bybit（只判断"当时有没有这个交易对"，不下载做计算）

- `api.binance.com`、`fapi.binance.com`、`api.bybit.com`（含 `api.bytick.com` 等镜像域名）在本环境直接请求均返回 451/403，提示"地域限制"（Binance: `Service unavailable from a restricted location`；Bybit: `CloudFront ... block access from your country`），换 `r.jina.ai` 代理请求同样被 Binance 拦截（说明代理出口 IP 也在受限地区），因此**未使用 Binance/Bybit 的行情/交易对信息 REST 接口**。
- 改用两家交易所公开、无地域限制的历史数据静态托管服务：
  - 币安现货：`https://s3-ap-northeast-1.amazonaws.com/data.binance.vision?prefix=data/spot/daily/klines/{TICKER}USDT/1m/&max-keys=3`（S3 ListBucket XML，直接读 `data.binance.vision` 官方文档里给的 S3 桶）。
  - 币安 U 本位合约：同上，`prefix=data/futures/um/daily/klines/{TICKER}USDT/1m/`。
  - Bybit U 本位永续：`https://public.bybit.com/trading/{TICKER}USDT/`（Bybit 官方公开成交数据归档，目录列表按日期文件名排序）。
  - 判断逻辑：取该 prefix/目录下**最早**一个日期的文件名，与公告 `published_utc` 的日期比较：最早文件日期 ≤ 公告日期 → `yes`；找到目录但最早日期晚于公告日期 → `no`；完全没有该 symbol 的目录/文件（404 或空列表）→ `no`；请求异常 → `unknown`。
  - 局限：这是"该交易对在历史数据归档里最早出现的日期"，不是"上线的精确时刻"，也不代表币安/Bybit 官方的 `onboardDate`/`launchTime` 字段（这两个字段所在的接口本身被地域拦截，拿不到）。多数币的数据归档更新有 1 天左右延迟，个别边界情况（公告当天即刻查询）可能有 ±1 天误差，本次窗口内暂未发现受此影响的行。

## 2. 字段含义

| 列 | 含义 |
|---|---|
| `exchange` | `upbit` / `bithumb` |
| `ticker` | 公告里给出的资产代码（原样摘取，见"同名不同币"一节） |
| `title_ko` | 公告原标题，韩文原样，未翻译 |
| `url` | Upbit 用 `https://www.upbit.com/service_center/notice?id={id}`；Bithumb 用 `https://feed.bithumb.com/notice/{id}` |
| `published_at_raw` | 官方接口原始字段值 + 字段名说明。Upbit 取 `first_listed_at`（公告**首次**发布时刻，不是可能因改稿而变动的 `listed_at`）；Bithumb 取 `publicationDateTime` |
| `published_utc` | 上一列换算成 UTC 的 ISO 时间，精确到秒 |
| `ts_precision` | 本次全部为 `second`（两家接口都给到秒） |
| `trading_start_raw` | 公告里写的开始交易时点原文。Upbit 取自公告正文表格"거래지원 개시 시점"列；若该公告发生过开盘时间变更，格式为"原始公告：...；最新变更（N次变更后）：..."，两个时间点都保留。Bithumb 优先取标题括注里的"(거래 오픈 ... 예정)"，标题没有的再取正文"거래 개시 시점 : ..."小节；仍取不到则留空 |
| `markets` | Upbit 从公告表格"마켓"列换算（KRW/BTC/USDT 以 \| 分隔）；Bithumb 固定为 `KRW`（已核实该分类下公告只涉及원화/KRW市场） |
| `prior_korean_krw_listing` | 见第 4 节方法说明 |
| `prior_note` | 支持上一列判断的依据（另一家交易所的公告时间，或当前市场列表核实结果） |
| `binance_spot_usdt` / `binance_usdm_perp` / `bybit_usdt_perp` | 公告发布时点该资产是否已有对应交易对，方法见 1.3 |
| `evidence_note` | 三个交易对判断的依据（用了哪个 ticker 查询、查到的最早日期），以及撤回/同名冲突等特殊说明 |

## 3. 时间戳的时区处理

- Upbit 接口原样返回带 `+09:00` 偏移的 ISO 字符串（KST），直接用 `datetime.fromisoformat` 解析再 `.astimezone(UTC)`，无需假设时区。
- Bithumb 接口返回 `YYYY-MM-DD HH:MM:SS` 不带时区，按韩国运营惯例视为 KST（`+09:00`）转换为 UTC；未在官方文档里看到显式时区声明，这是根据"面向韩国用户的交易所公告"这一惯例假设，未做额外交叉验证（可以用同一条公告在 Upbit/Bithumb 都出现的重叠事件、或公告正文里提到的"오후 X시"与 `publicationDateTime` 做一致性检查，但本次未逐条做）。
- 时间窗口筛选统一按转换后的 UTC 时间判断是否落在 2025-09-23T00:00:00Z ~ 2026-09-23T00:00:00Z（不含右端点，即到 2026-09-22 23:59:59Z）。
- `binance_spot_usdt` 等三列的比较用的是**日期**层面（UTC 日期），不是精确到秒，因为币安/Bybit 历史数据归档按天分文件，本身就没有更细粒度的"上线时刻"信息来源（見 1.3 局限说明）。

## 4. prior_korean_krw_listing 的判断方法

由于目标就是"该资产此前是否已在另一家韩国交易所 KRW 市场上线"，本次做法：

1. 用本次窗口内（2025-09-23~2026-09-22）**同时抓到的对方交易所"KRW 市场新增"事件列表**做交叉比对：若同一 ticker 在对方交易所窗口内的最早事件时间早于本条公告 → `yes`，`prior_note` 写对方交易所名称+韩国时间；若对方窗口内也有但更晚 → `no`（本条为先上）。
2. 若对方窗口内没找到同 ticker 的事件，再查对方交易所**当前（2026-09-23）**KRW 市场列表兜底：
   - 当前仍在对方 KRW 市场挂牌，但窗口内没抓到对应公告 → 说明大概率在窗口起点（2025-09-23）之前就已上线，标 `yes`，并在 `prior_note` 注明"具体日期未核实，早于窗口起点"；
   - 当前也不在对方 KRW 市场 → 标 `no`。
3. 无法归入以上两类（理论上不应出现，实测 Bithumb 侧出现 1 例，见下）标 `unknown`。

这个方法的已知局限：如果某资产在窗口内于对方交易所上线又下线（先上后又摘牌），"当前市场列表"兜底会误判为 `no`；本次未逐一核实是否存在这种情况，两家交易所都不常见主动摘牌新上资产，风险较低但未排除。

## 5. 遗漏和不确定之处

1. **Bithumb 的 `trading_start_raw` 已全部补全**：Bithumb 官方公告列表被 Cloudflare 保护，只能靠 `r.jina.ai` 代理逐条抓正文，且该代理访问 Bithumb 需要退避重试（约 12~25 秒一次，且会间歇性被拦截）。初稿受时间预算限制只补到 55/105，随后后台任务陆续跑完全部 70 条待抓详情页，并修正了标题解析逻辑（原先"TICKER1, TICKER2 거래 오픈 ..."这种多币共用一个开盘时间、且 ticker 前面还有别的 ticker 用逗号隔开的写法会被漏判），最终 105 条 Bithumb 行 `trading_start_raw` 全部有值（其中部分为标题括注给出、部分为正文"거래 개시 시점"小节给出，两种来源在抓取脚本 `build_bithumb_rows.py` 里都有区分记录，但 CSV 本身未单列来源字段）。Upbit 127 行同样全部有值（原始公告时间，若发生过开盘时间变更则同时保留"原始公告"与"最新变更"两个时间点，见第 2 节字段说明）。
2. **同名不同币（ticker 冲突）**，已识别并特殊处理：
   - `AMP`：Upbit 公告标题写作"AMP2"（与已有 AMP 区分），但表格里资产列仍显示"앰프(AMP)"；币安现货 AMPUSDT 最早数据是 2021-11-23，几乎可以确定是 Flexa 的老牌 AMP，不是本次新项目。三个交易对字段按 `unknown` 处理，并在 `evidence_note` 写明冲突。
   - `MET2`（Upbit）/ `MET`（Bithumb，同一项目 Meteora）：两家韩国交易所对同一项目用了不同的展示 ticker。按 `MET`（无后缀）去查币安/Bybit，因为查询结果（现货 2025-11-13、合约 2025-10-11、Bybit 2025-10-10）与两家韩国交易所约 2025-11-18 前后上线的时间顺序吻合（先上境外合约再上韩国现货），符合新币上线的一般规律，判断为同一资产；已在 `evidence_note` 注明改用哪个 ticker 查询。
   - `UP2`（Upbit）/`UP`（Bithumb，同一项目 Superform）：同上处理，按 `UP` 查询，币安/Bybit 均无数据，三列都是 `no`。
   - `META2`（Upbit 与 Bithumb 一致使用，项目 MetaDAO）：`META` 是极通用的字符串，可能对应多个不同项目，逐一核实项目身份超出本次检索范围，三个交易对字段按 `unknown` 处理。
   - 除以上四个已知案例外，只做了"标题内是否出现 ticker+数字"的自动扫描（只命中 AMP2 一例），**没有逐一核实全部 232 行的项目身份是否与币安/Bybit 同 ticker 交易对完全一致**，短代码（如 `F`、`O`、`RE`、`CC`、`IN`）存在潜在冲突但未见明显数据矛盾（多数在币安/Bybit 查询结果为 `NO_DATA`，即两边都没有对应交易对，冲突风险较小；小部分有数据的建议使用前再核对项目官网/合约地址）。
3. **币安/Bybit 的"最早数据日期"不等于官方 `onboardDate`/`launchTime`**：因为这两个字段所在的官方接口（`exchangeInfo`、`instruments-info`）被地域拦截，改用历史数据归档的最早文件日期代替，见 1.3 节局限说明。
4. **Bithumb 公告时区未做交叉验证**：按惯例假设 KST，未逐条核对（见第 3 节）。
5. **Upbit 一条公告（HEMI，id=6558）在发布后被撤回**：公告标题含"(헤미(HEMI) 거래지원 취소 안내)"，正文明确说明因安全事件取消上线，该资产从未实际开盘交易；该行仍保留在 CSV 中（`evidence_note` 首句注明撤回），供参照，同批公告中的 USELESS 未受影响、正常上线。
6. **窗口边界**：只统计公告**发布时间**（UTC）落在 2025-09-23~2026-09-22 的公告；个别公告的"거래지원 개시 시점/거래 개시 시점"（实际开盘时间）可能落在窗口外一两天（例如月底发公告、月初开盘），这属于正常情况，未做额外处理。
7. **Upbit 详情正文里"第一个表格"的解析陷阱**：个别公告在原始上市表格之前插入了与上市无关的表格（例如 id=6173 PRL 因"유통량 이슈"插入了钱包地址表），已改为按表头包含"디지털 자산"与"마켓"两列定位真正的上市表格，而不是取正文第一个表格；这个修正只针对 Upbit（Bithumb 正文不是表格结构，用小节标题定位，不受影响）。

> # [안내] 공지사항(Announcement) WebSocket 지원
>
> 안녕하세요. 업비트 개발자센터입니다.
>
> 업비트 공지사항을 WebSocket으로 실시간 수신할 수 있는 **공지사항(Announcement) 데이터 타입**이 추가됩니다.

> 신규 공지 게시 및 기존 공지 갱신 정보를 API 연동 환경에서 보다 편리하게 확인할 수 있습니다.

> * **데이터 타입:** `announcement`

> * Data Type Object의 `type`을 `announcement`로 지정하여 구독을 요청합니다.
> * 필요한 경우 `categories`, `include_body`를 함께 지정할 수 있습니다.
>
> ## 4. 유의사항
> * 신규 공지사항이 게시되거나 기존 공지사항이 갱신된 경우에만 데이터가 전송됩니다. 관련 이벤트가 발생하지 않는 동안 데이터가 수신되지 않는 것은 정상 동작입니다.

要点整理：

- **日期**：2026-08-31（周一）上线，与用户预期的"2026-08-31 前后"吻合。
- **是否需要认证**：需要。Endpoint 是 `wss://api.upbit.com/websocket/v1/private`——"private"端点，按 Upbit WebSocket 惯例需要 API Key 鉴权（区别于无需鉴权的 public 端点）。
- **与其他渠道到达时间的关系**：文档明确自称**不保证**与网页/App 端公告展示同步，原话是"채널별 전송 경로와 시스템 처리 상태, 시스템 보호를 위한 조치 등에 따라 수신 시점에 차이가 발생할 수 있습니다"（不同渠道的传输路径、系统处理状态、系统保护机制等都可能造成到达时间差异）。也就是说，这个 WebSocket 渠道本身不是官方承诺的"最快"渠道，对于想抢在网页公告之前拿到消息的场景，Upbit 官方没有给出时延保证。
