> 本文件说明 `raw/K2_events.csv` 的生成过程。本卡只收集事件清单，不做任何收益/跌幅计算，不下载价格数据。完成于 2026-09-23。

## 2. 筛选步骤

1. 取 `api.llama.fi/hacks` 全量 1283 条，按 `date` 在 `2024-04-01` 至 `2026-09-15`（含）且 `amount ≥ 1,000,000`（该字段即 amount_usd，已核对如 PlayDapp 记录 290,000,000 与公开报道一致）筛选，得 **230 条**，全部写入 CSV（含无代币的），按日期升序排列。
2. 代币解析：先用事件的 `defillamaId` 去匹配 `protocols.json` 的 `id`，取其 `symbol`/`gecko_id`；若空或未匹配，再用 `parentProtocolId` 去匹配 `lite/protocols2.json` 的 `parentProtocols[].id`。两步共解出 **82 条**有代币 symbol 的事件（唯一 symbol 75 个）。148 条判定为无代币（`none`），未做代币方向的人工二次核对（即：可能存在 DeFiLlama 数据本身缺失 defillamaId/parentProtocolId、但实际有代币的协议被漏判为 none 的情况，未逐条排查）。
3. 对 82 条中 `gecko_id` 为空的 38 条，用 CoinGecko `coins/list` 按 symbol 做候选匹配：唯一候选直接采用；多候选时按协议名与币种名的文本相似度选最高分且标注"候选 N 个，需人工核"；无候选或相似度过低的标注 `unknown(...)` 并说明原因。人工抽查确认了 GMX（排除"General Motors xStock"同 symbol 干扰）、YFI（排除同 symbol 冗余条目）等几处容易误判的候选，Kinto（symbol `K`）与 Velocore（symbol `VC`）在 CoinGecko 上找不到名称匹配的候选，未采信。
4. 四场所永续判断（只对 82 条有代币的事件做）：
   - **币安**：`fapi/v1/exchangeInfo` 在本环境不可访问（451，地域限制），改用 `data.binance.vision` 的 S3 列表接口，对每条事件的**攻击当日**分别查 `{SYM}USDT` 与 `1000{SYM}USDT` 两种交易对名的日 K 线 zip 文件是否存在，存在即视为该日已有永续（`yes`），两个变体都不存在视为 `no`。这与题目建议的"仅对已下架合约查当日文件"不同——因为本环境连现存合约清单接口都拿不到，只能对全部 82 条事件都用这个方法，等价于把"文件存在性"当作了"合约存在性"的唯一判据。
   - **Bybit**：完全不可访问，全部记 `unknown`。
   - **OKX**：用现存 `instType=SWAP` 列表里 `instId` 以 `-USDT-SWAP` 结尾的合约的 `listTime` 与攻击日期比较；`listTime ≤ 攻击日` 记 `yes`，`> 攻击日` 记 `no`；现存列表里找不到该 symbol 的记 `no`（附注：OKX 永续极少主动下架，这是一个经验性假设，不能完全排除历史上有过又下架的个别情况）。
   - **Hyperliquid**：先看 `meta.universe` 现存名单是否包含该 symbol；命中的再用 `candleSnapshot`（`interval=1d`）查历史。**关键发现**：Hyperliquid 的 `candleSnapshot` 会对某些资产（如 RUNE、GMX）回补远早于其永续实际上线时间的历史价格数据——这些早期 K 线的成交量 `v` 与成交笔数 `n` 均为 0，明显是指数/参考价格而非真实成交，直接用"最早一根 K 线"的日期会系统性地把上线时间估计得过早（例如 RUNE 最早 K 线是 2020-11-19，但 Hyperliquid 交易所本身 2023 年才上线）。本卡改用**首个 `n>0`（有真实成交笔数）的日 K 线**作为上线日代理指标，与攻击日比较得出 yes/no；现存名单里没有的记 `no`（同样是经验性假设，Hyperliquid 目前很少下架币种，未逐一验证有无例外）。
5. 只对四场所"至少一个为 yes"的 **29 条**事件，检索最早公开告警（推文/帖子）与攻击交易时间，写入 `hack_tx_time_utc`/`hack_tx_source`/`first_alert_url`/`first_alert_utc`/`alert_note`。检索方法：用 WebSearch 按"协议名+日期+PeckShield/SlowMist/CertiK/Cyvers/BlockSec/Ancilia/Hypernative/Blockaid/项目官方"等关键词找二级报道与安全公司博客，从中提取可定位的推文链接（`x.com/.../status/<id>`），再用 `((id >> 22) + 1288834974657)` 毫秒数换算成 UTC 时间（未打开推文本身）；找不到具体推文链接时，若能定位到安全公司/协议官方的博客原文（如 Hypernative、Resolv 官方 post-mortem）则作为 `first_alert_url` 但可能没有精确到秒的时间戳。

## 3. 遗漏与不确定之处（务必先读）

### 3.1 筛选环节

- `api.llama.fi/hacks` 的 `source` 字段在**全部 1283 条记录**（不止筛选出的 230 条）中都是空字符串，说明这个字段在当前版本 API 里已经不再填充/已废弃。`defillama.com/hacks` 网页被 Cloudflare 拦截，无法确认网页版是否有独立的来源链接数据源；因此 CSV 的 `source_link` 列**全部为空**，这不是逐条核实后判定为查不到，而是这个 API 字段本身对全量数据都是空的，判定为"DeFiLlama 目前不通过这个接口提供来源链接"。
- 148 条"无代币"事件**没有逐条人工核实**，可能有个别因 DeFiLlama 数据字段缺失（无 `defillamaId` 或 `parentProtocolId`）而被误判为 `none`、但实际存在代币的协议。

### 3.2 代币识别环节

- CoinGecko 兜底匹配对多候选 symbol（如 SPELL、GMX、YFI、Ribbon 等）用文本相似度选择，抽查了几个后确认方法可靠，但**没有逐条人工复核全部 38 条兜底匹配**，标了"候选 N 个，需人工核"的条目使用前建议复核。

### 3.3 永续判断环节

- **Bybit 全军覆没**：本环境的出口 IP 被 Bybit 相关的所有域名（`api.bybit.com`、`api.bytick.com`、`api.bybit.nl`、`api.bybitglobal.com`、`www.bybit.com`）判定为受限地区并拒绝访问，没能找到任何绕过方式。`bybit_usdt_perp` 列**全部**是 `unknown`，不是"没有"，是"没查到"。这会让"至少一个场所为 yes"的判断偏保守（Bybit 若单独覆盖了某些币种，会被漏掉）。
- **币安判断方法被迫替换**：官方 `exchangeInfo` 接口本环境不可访问（451），改用 `data.binance.vision` 逐日查文件是否存在。这个方法本身可靠（S3 直接列表，非网页爬取），但只查了**攻击当日单日**，没有查相邻日期，理论上如果文件系统在某天缺失（数据源故障）会被误判为 `no`；没有发现这种情况的迹象，但未做交叉验证。
- **Hyperliquid 的 candleSnapshot 陷阱**：已在 §2 步骤 4 详述，这是本次检索过程中发现的一个重要方法性问题——题目原建议"用 candleSnapshot 取最早日 K 判断上线日期"在存在历史指数数据回补的资产上是**错误的**，本卡改用"首个有真实成交量的日 K"，但这个改法本身依赖 `n`（成交笔数）字段的语义假设（`n=0` 即无真实成交），未经 Hyperliquid 官方文档逐条确认，建议主执行方如果要用这批数据做后续判断，对关键币种（尤其 RUNE、GMX）再做一次独立核实。
- **OKX/Hyperliquid 的"现存名单缺失=no"是经验性假设**，不是逐一核实的历史下架记录，两个交易所都缺乏公开的"历史曾上线又下架"合约清单接口。

### 3.4 告警与攻击时间环节（29 条里的大头缺口）

这是本卡里查得最不完整的部分，如实汇报：

- **29 条里只有 5 条**（Loopring、Bittensor、Radiant V2、Flow、SolvBTC）找到了可定位、可用推文 ID 或官方博客精确时间戳换算出 `first_alert_utc` 的一手来源；其余 24 条要么找到了"哪家安全公司/项目方最先报"但定位不到具体推文链接，要么连"谁最先报"都没查实。逐条原因见 CSV 的 `alert_note` 列。
- 几个需要特别注意的数据质量问题（已在对应行的 `alert_note` 里写明）：
  - **1inch（2025-03-07）**：检索中发现有两起名字很像的独立事件——2025 年 3 月的 1inch Fusion V1/TrustedVolumes 关联事件（本卡目标），和 2026 年 5 月同一攻击者对 TrustedVolumes 的**另一次**独立作案。找到的 `@1inch` 官方推文经 ID 换算落在 2026-05-07，属于后一起事件的官方回应，**没有**用于本行，避免张冠李戴；本行 `first_alert_url` 因此留空。
  - **Meteora DAMM V2（2026-01-17）**：多轮检索完全找不到这起事件的任何独立报道，无法确认 DeFiLlama 这条 150 万美元记录对应的具体经过，怀疑是报道极少的小事件，也不排除检索覆盖不足，建议主执行方直接核对 DeFiLlama 原始记录再决定是否使用这一行。
  - **SolvBTC / Resolv USR**：DeFiLlama 记录的日期（3-06 / 3-21）与二级报道里的攻击/检测时间（3-05 / 3-22）相差一天，怀疑是 DeFiLlama 记录口径（如链上确认日、UTC/本地时区）与实际攻击时间不同，未查清具体原因。
  - GMX、Radiant V2、Bittensor 三条虽有 `hack_tx_time_utc`，但来源都是二级报道转述官方时间线，**没有做链上交易哈希级别的一手核对**。

### 3.5 范围外未做的事

- 没有对"至少一个场所 unknown 但全部已查场所都是 no"的事件（如 Bybit 是 unknown、其余三个是 no 的情况）做进一步排查——按题目要求只深入查了"至少一个为 yes"的 29 条。如果之后 Bybit 变得可查，这批事件里可能会有新的 yes 出现，目前的"29 条"是**保守下界**，不是全集。

## 6. 补充：告警时间（第二轮，2026-09-23）

> 协调方要求给 29 条"至少一个场所为 yes"的事件尽量补齐 `first_alert_utc` 与 `hack_tx_time_utc`。本节记录这一轮的方法、逐行来源与新覆盖数。只改了这 29 行，其余 201 行未动。

### 6.1 新方法（比第一轮更有效）

第一轮主要靠 WebSearch 的自然语言摘要找推文，命中率低（29 条里只有 5 条有 `first_alert_utc`）。这一轮找到两个更可靠的路子：

1. **rekt.news 文章的 `__NEXT_DATA__` JSON**：rekt.news 页面本身是 Cloudflare 后面的 Next.js 应用，`curl` 直接拿到的 HTML 里正文是 JS 渲染的，但页面源码里嵌了一个 `<script id="__NEXT_DATA__" type="application/json">` 标签，里面是完整的文章 Markdown 原文（含所有内嵌链接）。用 `curl` 抓页面 + 正则取出这段 JSON 解析，就能拿到人工写的"Credit:"来源列表（通常是作者认定的信息来源，按大致时间顺序排列）、正文里明确标注的"Attack Transaction / Main Exploit Transaction"等交易哈希及其上下文。这比直接问 WebSearch"这个事件的推文链接是什么"稳定得多。
   - 先抓 `https://rekt.news/leaderboard`，同样解析出 `__NEXT_DATA__`，里面有全站 324 篇文章的 `{date, title, slug, tags, rekt:{amount,date}}` 列表，用协议名/日期/金额三者匹配，比逐个猜 slug 靠谱。
   - 29 条事件里 20 条在 rekt.news 有对应文章（Loopring、Bittensor、Banana Gun、Radiant V2、1inch、Abracadabra×2、Cetus、GMX、WOO X、UXLINK、Balancer V2、Saga、IoTeX、SolvBTC、Venus、Resolv、Drift、Kelp、THORChain、Humanity）；Yala、Trust Wallet、Meteora、Raydium（本次这起）、Taiko、Across、Flow、Yearn 这 8 条没有对应文章（Raydium rekt.news 只有一篇 2022 年的旧文章，与本次 2026-06 事件无关）。
2. **推文 ID 换算**：对 rekt.news Credit 列表里的每个 `x.com/<handle>/status/<id>` 链接算出 `((id >> 22) + 1288834974657)` 毫秒时间戳，按时间排序，人工排除掉明显与本次事件时间对不上的早期无关引用（例如某账号几周前的背景推文被作者引用在同一篇文章里），取时间最早且主题相关的一条作为 `first_alert_utc`。
3. **链上交易时间核实 `hack_tx_time_utc`**：rekt.news 正文里经常直接标注"Attack Transaction: 0x..."并附区块浏览器链接。用免费公共 RPC 节点（不用 Etherscan API key）查区块时间：
   - Ethereum: `https://ethereum.publicnode.com`
   - Arbitrum: `https://arb1.arbitrum.io/rpc`
   - BSC: `https://bsc-dataseed.binance.org`
   - Base: `https://mainnet.base.org`
   - Solana: `https://api.mainnet-beta.solana.com`（`getTransaction` 返回 `blockTime`）
   
   方法：先 `eth_getTransactionByHash` 拿 `blockNumber`，再 `eth_getBlockByNumber` 拿 `timestamp`（Solana 直接从 `getTransaction` 拿 `blockTime`）。这是一手链上数据，比任何二级报道都可靠，多处与二级报道/官方复盘的说法做了交叉验证，全部吻合或接近吻合（见下表 SolvBTC、Resolv、GMX 三条尤其吻合）。
   - **踩过的坑**：GMX 的 rekt.news 正文里有三笔交易（Initial Funding / Attack Contract Deployment / Main Exploit Transaction），只有第三笔是真正的攻击时刻，前两笔是准备阶段；Drift 的"Origin transaction"实际上是三周前的 Tornado Cash 资金准备交易（链上核实为 2026-03-11，而非攻击当天 2026-04-01），真正的攻击是 Solana 链上"128 Seconds"攻击链的第一步，另外找到才核实对；1inch 的"attacker's wallet funded through Tornado Cash"链接也是准备阶段，真正第一笔攻击交易在正文"series of meticulously crafted transactions"列表里另外给出。**结论：rekt.news 里出现的第一个链接不一定是攻击交易本身，需要读上下文标签（Attack/Origin/Funding 等词）才能判断，机械取第一个链接会取错。**
4. **Telegram 公开频道时间戳**：Trust Wallet 一条，ZachXBT 是在 Telegram 频道（`t.me/investigations`）而非 X 首发，该频道的公开预览页 `https://t.me/s/investigations` 每条消息有 `<time datetime="...">` 标签，直接读取即可，不需要推文 ID 换算。
