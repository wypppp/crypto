## 2. 选择

| 方案 | 内容 | 能回答 | 估计费用（试用期后，Plus 档 $399／月含 25,000 credits，超出每 100 credits $1.596） |
|---|---|---|---|
| A | meta 全部币 | 元数据想法（C6、C7 同名原版的分组与到达时钟、U16 语义）的母体与按时点摘要；任何入场规则在 30 秒／5 分钟／1 小时／24 小时四个时点的粗粒度状态 | 约 2 万 credits：Plus 一个月 |
| B | A＋trades 前 100 笔抽 1/16 | 加上逐笔：入场时点、我方成交价、签名者与钱包关系（U32～U37）、重复点火（U39），样本是无条件随机抽的 | 约 3.8 万：约 $600 一个月 |
| C | A＋trades 前 100 笔抽 1/8 | 同 B，尾部事件多一倍 | 约 5.6 万：约 $900 一个月，或分两个月 |
| D | 全部币前 100 笔 | 同 C，不抽样 | 约 28 万 credits，约 $4,500，且下载约 86 小时；不建议 |

**建议**：B。理由：右尾想法的入场多在前几十笔之内（每币中位只有 9 笔），前 100 笔覆盖绝大多数入场时点；按币哈希抽样是无条件的，不按后来是否毕业或是否大涨筛，估计不偏；1/16 已有约 92 万个币，每周约 1.1 万个，开发周上的尾部事件数够做第一轮筛选；某个想法需要更多尾部样本时，再对开发周补取 1/8。

## 3. 设计要点（请 GPT 审）

1. **母体**：曲线创建时刻在该 UTC 周的全部 pump 新币；与 DQ-37 检验周同一归属口径（按币创建周）；排除封存周创建的币与币安留出同名币（代号规范化同 DQ-35 v2）。
2. **meta 层**：创建事件字段（名称、代号、URI、创建者、签名者、交易号、代币程序、mayhem、cashback、计价资产、创建时虚拟储备；后五项 2026 年才有，2025 年的币为空）；曲线完成时刻（扫到 2026-09-29）；四个时点的笔数、买入笔数、近似用户数、买卖 SOL、时点前最后一笔成交后的虚拟储备、到时点为止的最高虚拟 SOL。
3. **trades 层**：前 N 笔，排序键 `ord`（slot、交易内序号、外层、内层指令），在 SQL 里用 BIGINT 排序，**输出时转 varchar**——Dune API 把超过 2^53 的 BIGINT 当浮点序列化，会丢低位（10-03 冒烟发现：57 行看似重复，实为丢位）。成交前储备＝成交后 ∓ 金额：非 mayhem 币逐笔吻合；**mayhem 币不吻合**（虚拟 SOL 变动约为金额的 437 倍，DQ-35 README §1b），mayhem 币的估值由底座单独处理。
4. **截断**：trades 只取创建后 7 天内；第 N 笔晚于 7 天的币右截断（记“7 天内不足 N 笔”）。
5. **抽样**：`mod(from_big_endian_32(substr(sha256(to_utf8(mint)),1,4)), K) = 0`。抽样规则与检验周规则互相独立。
6. **只存不分析**；检验周的币照存，开发代码用 `weeks.filter_dev` 先去掉。
7. 运行与核对沿用 DQ-35 v2 的做法：新标签、按清单逐片核对、同一 SQL 选一片跑两次逐行一致、小样本逐笔重算。
