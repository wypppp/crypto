## 1. 结论先行

1. **S3 一对一条 SQL，只下载统计量。**状态分箱、命中、成熟、自身、同层期望、合格、入选都在 SQL 里算，不下载逐行明细（§2）。
2. **实体归并选甲（上传映射表）。**乙在 SQL 里算不出单钱包实体的得分，要么两遍查询，要么导出逐行（§4）。
3. **与冻结卡 §8 的参照逐项相等**：DuckDB 构造数据与 12 组随机数据上，SQL 的每个输出都与参照相同。改动 W+1 的任何数据，入选集合不变。共 25 项测试（§5）。
4. **五处实现定义**是冻结卡没写死的，交 GPT 窄范围审（§3）。它们不改冻结卡的规则。
5. **真实数据上的核对还没做。**试跑被本机权限检查拦下，没有执行（§6）。
6. **作废**：v2 §6、v3 §6 的“上限与硬停 22,000、24,000”，冻结卡 v4 §12 第 6 条的“本期预算上限 15,000”。额度一律以 Dune 用量接口的实时读数为准，每条付费查询逐条批准（02 §10.9 补注）。三份文件都已冻结，所以在这里和 README 里标注，不改原文。

## 2. 一条查询做什么（`s3_sql.build_s3`）

| CTE | 内容 |
|---|---|
| `emap` | 钱包 → 实体代表（只含多钱包实体；全量用上传的表，试跑用内联 VALUES） |
| `cw` | 窗口币：W 与 W+1 两周创建、按币哈希抽样的币。观察终点＝min(创建＋30 天, 10-05, 数据止点)；W 的币再截到截点 |
| `tr`、`tw` | 曲线成交（事件表），逐币 [创建, 观察终点)；前 60 秒净买入（同汇总版 CYC 的窗口写法） |
| `ub`、`fr` | 曲线与 PumpSwap 的成熟买入，映射到实体；每个“实体 × 币”只留顺序键最小的一笔 |
| `ce`、`lb` | 毕业事件（全部，不只第一条）；逐事件判命中与自身 |
| `wq`、`bd`、`sr` | 分箱边界（只用 W 的曲线行）与层的键 |
| `ss`、`rx`、`sc` | 层的 (n, K)；W 上每个实体的行数、命中、得分 |
| `el`、`kq`、`cd`、**`sel`** | 合格、⌈合格数/10⌉、候选排序、入选。`sel` 只读 W 的行 |
| `w1`、`a1` | W+1 的行与入选实体在 W+1 的行数、命中 |

**输出**（`OUT_COLS`）：

- C 行：每个候选（得分 >0）一行，含行数、命中、得分、名次、是否入选，W+1 的行数与命中，以及精确得分所需的两列。
- G 行：W+1 中每个含入选实体行的层一行，即 (n, K, m, k)。
- N 行：汇总计数、分箱边界和应为 0 的核对计数。

本机由 G 行算 T＝Σ(k − m·K/n)（精确分数），零分布按超几何 (n, K, m) 抽 9,999 次（a_riskset.set_test 的同一抽法）。

## 3. 冻结卡没写死的五处实现定义（交 GPT 审）

| # | 项 | 定义 | 理由 |
|---|---|---|---|
| 1 | 分箱边界 | 每对只用 W 的曲线行（实体合并后、首笔成熟买入）求边界，W+1 用同一组。最近秩法：第 q 个 n 分位边界＝升序第 ⌈q·N/n⌉ 个值；箱号＝严格大于的边界数 | 卡写“只用允许域、形成期内的分布”；最近秩法在 SQL 与 Python 里都精确、可复现 |
| 2 | 进度变量 | 成交前的真实代币储备（成交后＋本笔代币）。进度＝1−它÷初始储备；初始储备相同时，二者的十分位一一对应 | 不依赖创建事件的初始储备字段（旧事件可能缺） |
| 3 | 其余三项 | 前 60 秒净买入、本笔大小（买入付出的 SOL，含两费）各取 W 的三分位；UTC 小时按 0–5、6–11、12–17、18–23 分四档 | 卡只写“三档”“四档” |
| 4 | PumpSwap 行 | 状态记 −1，不按池深分箱 | 毕业后的买入不可能在 30 分钟内碰到毕业，层内 K＝0：期望为 0，对得分、T 与零分布都没有贡献，任何分法结果相同；它只计入合格行数与“W+1 是否活跃”。SQL 另报 `chk_amm_event`（应为 0） |
| 5 | 得分的表示 | 以 1/D 为单位记整数，D＝lcm(1..60)。层大小 ≤60 时期望 K/n 精确；更大的层向下取整，另出精确项之和与不精确项的 n:K 列表。本机算出每个候选的精确得分（分数），核对 SQL 的入选；不同就停下 | Trino 没有分数类型，浮点和定点小数都会把真并列算成不并列 |

**实体归并的规则**（`s3_ref.entities`，照 DQ-26 `entities.py`）：

- **边的来源**：W 的事前图（截点＝W+1 周一），只用 S、G、T 三类。C 边只给 L 标签用，S3 不用（EDGE 新增 `edge_kinds="SGT"`）。
- **服务节点**：S、T 边的任一端，在该类边里的不同对手超过 200 个，或在交易所名单（DQ-21 `Q_cex_all`，166 个）里，就不经它合并。G 边的来源扇出超过 200、扇出缺失或在交易所名单里，也不用。
- **代表与范围**：实体代表取组内字典序最小的地址。W 与 W+1 都用这同一张映射表；W+1 新出现的钱包都是单钱包实体。
- **跨对去重**：按实体代表。

**自身触发的“关联体”**：S3 取空集。逐事件自身只认“触发者属于同一实体”与“与这笔买入同一笔交易”。同一实体的钱包已在归并时合在一起。

## 4. 实体归并：甲还是乙

**选甲：本机并查集，把多钱包实体的“钱包 → 实体”对照上传成 Dune 表，S3 的 SQL 连接它。**

乙的问题在得分上。单钱包实体的得分＝命中 − Σ 同层 K/n，而 K、n 要把多钱包实体合并后的行算进去。多钱包实体的行在本机才合并，所以 SQL 里算不出单钱包实体的得分。乙要么跑两遍，第一遍出层计数，第二遍带着本机算好的期望再算；要么导出所有含可合并钱包的层的逐行数据。前者多一倍执行，后者回到下载明细。甲一遍算完，与参照的等价最直接。

**上传的事实**（Dune 文档与用量接口，0 credits 核对）：

- **费用**：建一张上传表扣 10 credits；单次上传上限 500 MB。
- **存储**：本账号存储上限 15 GB，已用 0；存储不按 credits 计费。
- **公开与否**：上传接口有 `is_private` 参数。本账号能否建私有表，要真建一次才知道（10 credits，不在本轮批准内）。若只能公开，映射表会公开。它是从公开链上转账算出来的“钱包 → 实体代表”，不含任何结果；报告里会写明。
- **大小**：三对合成一张表（列：对、钱包、代表），预计几十万行，几十 MB 以内。
