## 3. 四件事

### 3.1 时点

存档有三个时点，只有第二个能核到：

| 时点 | 能否得到 | 本周实测 |
|---|---|---|
| 上榜时刻（来源的发布时点） | 不能。存档只记“当天上过榜的标题” | — |
| 存档可得时点（首次出现在某次提交里） | 能，精确到提交 | 全周 53 次提交；间隔中位 2.7 小时，最长 6.2 小时 |
| 本地取得时点 | 回放时等于提交时刻加拉取时延；拉取可以做到分钟级 | — |

- 上榜时刻只知道一个区间：(上一次提交, 首次出现的提交]。1,449 个事件里，左截断（全周第一次提交里就有）51 个；其余的区间宽度中位 4.3 小时，第 90 分位 5.2 小时。
- 提交按北京日期分文件。一天的最后一次提交可能早于午夜 5.7 小时；这段时间上榜又在午夜前下榜的标题，存档里没有。所以存档**会漏事件**，漏掉的比例无法从存档本身算出。
- 提交时刻由 GitHub Actions 的机器人写入，作者时刻等于提交时刻。它是声称的时刻；GitHub 服务器端的推送记录只保留约 90 天，2026-06 的已不能独立核实。

### 3.2 修订

- 每个日文件只增不删：全周 0 次删除，0 次链接改变。标题原文没有被事后修订。
- 文件没有热度值，只有标题与链接；链接里带首次抓取时的榜位（部分条目）。所以不存在“计数是抓取时的当前值”的问题，但也没有热度序列。

### 3.3 候选币

规则（写死在脚本里）：决策时刻＝存档首现时刻；候选＝决策前 7 天内创建、开盘时刻（有记录时）不晚于决策时刻的中文名币；名称或代号规范化后是标题的子串。长度 ≥2 记宽松，≥4 记严格。创建时刻先过入口过滤，窗口内的中文名币 23,747 个。

| 项 | 宽松（≥2 字） | 严格（≥4 字） |
|---|---|---|
| 事件总数（全周去重） | 1,449 | 1,449 |
| 没有候选的事件 | 959（66%） | 1,390（96%） |
| 有候选的事件 | 490 | 59 |
| 有候选时，候选数中位 | 2 | 2 |

- 宽松匹配噪声大：“来了”“暴跌”这类常用词能对上 30～44 个币。严格匹配才接近“同一事物”。正式的映射要用模型（见 3.4），这里只给分母的量级。
- 只覆盖中文名币。非中文名币在 DQ-29 只抽了 5%，英文同名币没有计入。

**“市场在存档之前就发了币”**：不计左截断，有严格候选的事件 56 个。其中 19 个（34%）至少有一个同名币创建在上榜区间内，即上一次提交之后、存档首现之前；这 43 个币早于存档首现的时间中位 1.9 小时（第 10～90 分位 0.6～4.4 小时）。例：“其实人是一根香蕉”的 9 个同名币，在存档出现前 3.5～4.4 小时就已创建。

### 3.4 模型

- 映射与分类按 02 §10.13：本地开源模型，发布日早于样本起点（例如 2024 年发布的 Qwen2.5 系列，早于 2025-07 起的 four.meme 中文币），固定权重哈希，离线运行；只做“标题与币名是否指同一事物”和题材分类，不给结局或叙事好坏打分。
- 运行位置：本机 GPU，离线。时延：每批标题秒级；回放时相对 2～6 小时的存档时延可以忽略。离线日级处理不算分钟级反应能力（导航 §9.3）。

## 4. 两份合同的读法

**O3a 传递滞后（这个来源）：暂不投入。**

- 存档的可得时点比上榜晚 2～6 小时，而同名币常在这段时间里就被发出。按存档回放，我们的决策时刻已经落在“映射完成”之后。
- 只关闭“以 GitHub 微博热搜存档作信号源”的 O3a 实现。O3a 本身未被否定：上榜时刻本身有没有领先，存档测不了。
- 重开条件（补证项）：分钟级的前向采集——每分钟抓取热搜榜，同时记录 four.meme 新币的创建流（公开 BSC 节点，免费）。0 credits，但要几周日历时间，并且是前向采集，开始前须用户裁决。

**O3b 持续需求：可写卡（有两个前提）。**

- 可回放的特征：标题原文（不修订）、存档首现时刻、首次抓取的榜位（部分条目）、在榜持续的天数（只用决策时已发生的部分）、本地模型给出的题材分类。
- 结局的数据在本地：DQ-29 `SAVE_BUCKETS`（创建后 7 天的曲线分桶，首小时每分钟）与 `SAVE_POST`（毕业后 30 天小时价）。本周没有读这两份。
- 前提一：DQ-29 的提取 SQL 未审（README 已标），用于结局之前须交 GPT 审，审出的字段先修正。
- 前提二：开发周跨 2025-07～2026-09，中文名币从 2025-07 才出现。检验周、封存周、10-05 起的币在入口排除。
