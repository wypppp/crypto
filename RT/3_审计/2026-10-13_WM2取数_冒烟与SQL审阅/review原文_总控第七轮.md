二、S3 的取数：在 SQL 里算到统计量，只下载统计量
依据冒烟实数：CYCC 一天执行 0.44 credits，导出 23.7 MB 约 55 credits，导出占九成九。盘点 §4 的 2,500～3,000 几乎全是下载费，下载的是 S3 用不到的逐行明细。

冻结卡 v4 §8 的 S3 只需要：

- W：每个实体的成熟行数（判合格）与得分 Σ(命中 − 同层期望)；
- W+1：只对含入选实体行的层，输出 (n_s, K_s, m_s, k_s)，即层内行数、层内命中数、入选实体行数、入选实体命中数。层内置换的零分布就是超几何 (n_s, K_s, m_s)，9,999 次在本机抽；
- PumpSwap 阶段的首笔买入不可能在 30 分钟内碰到毕业，层内 K＝0，对 T 和零分布都没有贡献，只计入合格行数。所以 CYCA 只要每实体的计数，不要逐行。

状态分箱、命中、成熟、自身标记、同层期望、合格、入选（含并列按 sha256 定序）都在 SQL 里算。选集只用 W 与截点前的信息，写成单独的 CTE；加测试证明改动 W+1 的任何数据都不改变入选集合。

难点是钱包归并成实体，必须在取首笔买入与分层之前完成。两条路，你选一条并写明理由：

- 甲（上传）：下载 EDGE v3，本机并查集，把多钱包实体的“钱包→实体”对照上传成 Dune 表，S3 的 SQL 连接它。先查清：本账号能否上传、上传是否扣 credits、表是否公开（若公开，报告里写明）。
- 乙（不上传）：S3 的 SQL 内联 EDGE v3 的边，标出“有可合并边的钱包”。这些钱包的首笔成熟买入逐行导出（紧凑编码），本机归并；其余钱包都是单钱包实体，在 SQL 里汇总，层计数只算它们。本机把两部分合并后，必须精确等于实体口径。

不论哪条路，结果必须与冻结卡 §8 的 Python 参照实现逐项相等。这是实现，不改冻结卡规则。写进取数附录 v4，在任何全量结果之前提交。如果 0 credits 阶段就发现做不到精确等价，停下报告。

1. 0 credits：写 SQL 与等价测试。构造数据至少覆盖：多钱包实体同买一币、自身触发、未成熟、毕业后买入、得分并列。

   - 两者在试跑范围内各双跑一次，核一致。
