## 3. 第二节：S3 的取法

| 项 | 处置 |
|---|---|
| 在 SQL 里算到统计量 | `s3_sql.py`：一对一条。输出 C 行（候选实体）、G 行（W+1 含入选行的层 (n, K, m, k)）、N 行（汇总与核对）。见取数附录 v4 §2 |
| CYCA 只要计数 | PumpSwap 行不分箱，只计入合格行数与“W+1 是否活跃”；SQL 另报 `chk_amm_event`（应为 0） |
| 选集写成单独的 CTE | `sel` 只读 W 的行。测试：换掉 W+1 的全部数据、给 W 的币加截点之后的成交与毕业，候选、得分、名次、入选都不变 |
| 甲还是乙 | **选甲（上传）**。乙算不出单钱包实体的得分（期望要把多钱包实体的行算进去），要么两遍，要么导出逐行。上传的事实见附录 v4 §4：建表 10 credits，存储上限 15 GB，私有与否要真建一次才知道 |
| 与 Python 参照逐项相等 | `s3_ref.reference` 直接调用冻结的 `a_riskset.label`、`collapse`。构造数据与 12 组随机数据上逐项相等；与冻结的 `select_set`、`set_statistic` 一致 |
| 取数附录 v4 | 已写，全量之前提交 |

**冻结卡没写死的五处**（附录 v4 §3）：分箱边界、进度变量、其余三项的档、PumpSwap 行的层、得分的整数表示。另有实体归并规则与自身触发的“关联体”取空集。它们都不改卡的规则，交 GPT 窄范围审时一并列出。

**一处做到精确等价的关键**：Trino 没有分数类型。浮点或定点小数会把真并列算成不并列，并列按 sha256 定序就会错。改为以 1/D 为单位记整数（D＝lcm(1..60)），大于 60 行的层另出不精确项的 n:K 列表。本机由此算出每个候选的精确得分，核对 SQL 的入选；不同就停下。测试里一个 61 行的层验证了这条路。
