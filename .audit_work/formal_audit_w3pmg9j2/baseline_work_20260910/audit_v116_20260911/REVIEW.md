## P1：校验接口失败必须与实际状态不符分开

位置：`pilot_measure.py:368`、`:385`、`:1016`、`:1067`、`:1224`、`:1232`。

首轮候选 491473 在 `state_validation_exit` 调用 token0 时遇到 TLS EOF，随后 `restore_check` 又遇到一次 TLS EOF，最终 state_validation_failed。第二轮同候选在入场校验取 router 代码时遇到 RemoteDisconnected，却为 data_missing。这些原始错误均能在 `error_inventory.json` 中按阶段找到。

对同一受控传输错误执行完整 measure 路径，结果如下；所有错误场景都是退出 1、检查点不标完成、证据完整，没有发真实请求：

| 注入位置 | 当前 state | validation_passed | 额外观察 |
|---|---|---|---|
| 入场校验 getCode | data_missing | **true** | 校验实际未完成，却被默认视为通过 |
| 入场身份调用 | state_validation_failed | false | 异常被加入 identity_call_failed |
| 出场校验 getCode | state_validation_failed | false | 无原值，却被恢复检查报成 4 条 code/balance persisted |
| 出场身份调用 | state_validation_failed | false | 接口故障被归入不符列表 |
| 恢复复读 | state_validation_failed | false | 未取得复读结果也被写成校验失败 |

出场 getCode 场景的“持久化”结论是假的：异常导致出场 `wallet_clean` 没存入结果，恢复检查用 `before.get(key,{})` 得到缺失值，再把真实的 `0x` / `0x0` 与 None 比较，于是报告持久化。受控链没有任何状态变化。

**审核决定：应修。** 按既有 §3，接口传输故障导致必需校验无法完成，应归 data_missing，细记失败阶段、error_kind、校验状态 unavailable；恢复阶段同样适用。未知不得写成实际状态不符，也不得标 validation_passed=true。

建议区分 `passed / failed / unavailable / not_applicable`，或等价的明确字段：

- 有完整可比证据且确实不一致，才记 state_validation_failed；既有失败证据与后来接口故障并存时，两者都保留。
- 校验开始但未完成，记录 unavailable，并继续阻断完成、经济资格、验收和续跑跳过。
- no_mint 等路径无需进行的校验，记录 not_applicable，保留原先正确的流程完成行为。
- 缺基准原值时不得做“持久化不符”比较；保留已取得的部分证据及尚缺哪些项。
- 保留已发生的买卖阶段与成本；本轮受控恢复失败后已有买卖成本仍在，不应修分类时抹掉。
- 解码错误、预算耗尽、停机保持各自原因，不能把所有异常一概归接口断连。

验收应包含上述五条完整流程，以及真实身份不符／状态变化和 no_mint 对照，检查状态、validation 标记、退出码、成本、证据和检查点。旧真链记录保留原字节，以勘误说明，不追改其分类。

## 报告数字的边界与更正

### 错误率与 300 样本

`6/2290` 可以复算，但范围是**具有完整结果的六次运行中的 RPC**。两轮执行证据另外还有两次启动即失败的 RPC，均为 TLS EOF。纳入它们是 **8/2292 ≈ 0.349%**。另外 preflight.json 自报 2 次 RPC，不能把 2292 泛称所有前置操作在内的总消耗；此处分母明确限定为读取到的逐条 RPC 执行证据。

```
1 - (1 - 6/2290)^105 = 24.0785%
```

算术正确，但依赖每次调用独立同分布、风险稳定、候选完整路径近似固定 105 次等假设。它不是本轮直接测出的候选失败率。首轮四个 TLS 错误集中在约十秒内，已有聚集现象；候选路径长短不同，no_mint 只用很少调用，失败还会提前截断路径；两种调度反复测的是同八个候选。

可以直接报告第二轮首遍串行 1/8、并行 2/8 因传输错误未完成，以及续跑又有一次失败；不能把它们当 16 个独立候选，也不能据此预测 300 个候选约 70 个失败。24% 如保留，只能明确标为**独立同分布假设下的预算压力情景**。

应按实际完整尝试、失败发生阶段、续跑次数和窗口内聚集情况留出分档预算，并定义超预算时停机／不完整交付。当前记录不足以确定未来稳定故障率，或证明故障归因于端点、网络、新连接代码中的哪一方；也不能预先保证“数千次 A/B”足以确证原因。

### 并行耗时

首遍 438.1/771.0 = **56.8%** 是本次有效描述，但两侧首遍完成集合不同（6/8 与 7/8）。计入各自补齐到 8/8 的续跑，子进程墙钟之和为：

- 串行：771.0 + 131.2 = **902.2s**；
- 两路并行：438.1 + 147.2 + 129.7 = **715.0s**，约串行的 **79.3%**。

两者均不含人工间隔／额外等待，也不是主动工时；这只是本次开发样本记录，不外推 300 样本的速度或完成预算。

### 首轮退出码

首轮 parallel 和 resume_serial 的 runs.jsonl **实际都记 exit=1**，stderr 有 traceback，证据无 abort/footer。因此“退出码不在 0/1/2/3 里”不成立；准确说法是未捕获异常以 1 退出，违反了预期的前置失败分类和证据收尾语义。

v1.16 新处理路径在两类启动错误的离线受控守卫中均返回 2、留下 endpoint_unreachable abort 并撤销设施；本轮复跑这些守卫通过。未声称它已在真实启动故障上再次触发。旧版逆向还原的六条失败未在本轮重新独立运行，不冒充本轮结果。
